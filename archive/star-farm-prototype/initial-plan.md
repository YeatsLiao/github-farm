2026-11-15。木屋菜园、溪边果园、谷仓牧场的 0 Stars 构图已确认。新版起步模板由仓库 ID 选择，0 至 300 Stars 共九档，200 Stars 时镜头展开到新增作业区。本地命令 `npm run build:star-farm -- --id demo-0 --repo example/farm --stars 25` 可直接输出卡片。后续将完整的后期成长规则移入三个模板，再接真实仓库数据与 README 图片接口。

2026-11-14。成长改为每 100 Stars 一档，0 到 5,000 Stars 共 51 档。同一仓库的完整成长对照分为五张。5 项定向测试通过，覆盖 50 个种子和 50 次阶段过渡。

## 1. 产品与交付边界

- 核心：每个公开 GitHub 仓库以稳定随机种子生成独立的 A 风格农场，再随 Star 数在原地图上成长。
- 使用：用户粘贴一行 Markdown，无须配置 Action、Token 或登录。
- v1 使用春日静态 PNG，每 100 Stars 推进一个成长档位，5,000 Stars 解锁风车。公开图片接口仍在计划内。
- 由统一素材和规则合成；不在请求时调用生图模型。
- 暂不做：GIF、四季、自由布置、账号体系、私有仓库、经营玩法、完整详情站。
- 点击卡片先进入原 GitHub 仓库。独立农场详情页后续再做。

部署后的接口合同（example.com 只是占位，不是已上线地址）：

```markdown
[![Star Farm](https://farm.example.com/v1/farm/OWNER/REPO.png)](https://github.com/OWNER/REPO)
```

## 2. 设计稿与信息布局

- [A 风格基准](../design/star-farm-v1/style-a-reference.png)
- [README 信息卡](../design/star-farm-v1/readme-card.png)
- [低、中、高阶段对照](../design/star-farm-v1/growth-stages.png)
- [生成方式及完整提示词](../design/star-farm-v1/README.md)

以上均为概念稿，32 / 320 / 1,280 Stars 等为演示值，不代表实际账号数据。
生图稿中地形和物件存在细微偏差；正式渲染中同一仓库跨阶段共用地形和锚点，所有仓库统一美术比例；不同仓库允许不同布局。不能把三张生图直接作为最终实现。

正式卡片：逻辑尺寸 640×480，导出 1280×960 PNG，README 建议展示宽 640。
顶部 48px：仓库名与固定短句；中间 360px：农场；底部 72px：数据与成长目标。
全部尺寸均指逻辑像素，卡片信息由代码绘制，不烘焙进美术图。
长仓库名最多两行并省略；v1 不显示任意长度项目描述，不堆叠 Fork、Issue 等次要指标。
目标：640px 宽时主信息可读；窄屏至少能辨认仓库名、Star 数和阶段。

| 信息 | 显示规则 |
|---|---|
| 仓库 | owner / repo，保留 GitHub 返回的大小写 |
| Stars | 当前总数，完整千位分隔，不用模糊的 1.2k |
| NEW STARS / 7D | 历史接口最近七个完整日桶的获星数之和；不是总数净增 |
| STAGE | 当前档位和总档位，例如 STAGE 05 / 51 |
| NEXT | 下一阶段或里程碑及差额；达到最终里程碑显示 FULLY GROWN |
| Updated | 数据成功获取时间，明确 UTC；不以图片请求时间冒充更新 |
| 异常 | 历史不可用显示 --；旧缓存显示 STALE；不伪造零值或演示数据 |

日桶边界沿用 GitHub 历史接口口径，不承诺与 UTC 自然日完全一致；更新时间独立使用 UTC。
v1 卡片用英文标签兼容国际 README；保留 Unicode 仓库名的字体回退。

## 3. 成长规则

每 100 Stars 推进一档。具体的播种、收成、果树和设施阈值统一写在 `config/growth.json`。

| Stars | 部分里程碑 |
|---:|---|
| 0–500 | 第一块菜地从整地开始，两排作物依次播种、长成，400 建井 |
| 600–1,400 | 栽第一棵果树，开第二块菜地，1,000 建鸡舍，随后布置院落并升级小屋 |
| 1,500–2,600 | 扩展果园，添鸡和鸭，开第三块菜地，2,000 把鸡舍原地升级为谷仓 |
| 2,700–4,800 | 逐块补种伴生作物，更新收成与物资，果园进入成熟期 |
| 4,900–5,000 | 备好风车工位的土路与物资，5,000 建成风车 |

- 5,000 Stars 为当前地图的第 51 档。卡片继续显示实际 Star 总数，场景保持成熟形态。
- 32、320、1,280、5,000 为固定演示样本；边界另测 0、99、100、999、1,000、4,999。
- 总 Star 决定阶段；近7天获星仅作信息展示，v1 不再叠加另一套视觉映射。
- 阶段按当前 Star 计算；掉星跨阈值会回到对应阶段，v1 不持久化“曾解锁”状态。
- 同仓库同数据同版本输出可复现；仓库自己的房屋、池岸和主路不移动，只在本仓库蓝图预留位置扩建。
- 仓库 ID 作为稳定随机种子，控制地形方案、区域/建筑位置和元素组合；Star 数不参与底图种子计算。
- 低 Star 农场也必须完整好看；高 Star 农场也要留出道路和空地。

### 3.1 每仓库一个种子：布局先生成，成长后叠加

2026-11-05 评审修订：不同仓库拥有不同地图，并在各自初始地图上生长。本条替代此前“种子仅控制配色”的限制。

“种子”是随机生成器的固定输入，不是作物种子数量。

```text
仓库稳定ID + 布局版本 → 随机种子 → 本仓库完整蓝图
完整蓝图 + 当前Star数 → 当前解锁物件和生长状态 → 信息卡
```

- 先从少量经过审美验证的区域拓扑中选择，再生成池岸、主屋、区域位置和物件组合。
- 生成之初规划最终扩建空间、道路连接和物件稳定ID；低阶段用草地和可替换野花呈现未建区域，不展示施工占位框。
- 每个物件用自身稳定ID派生随机序列；加入新物件不能改变已有物件的位置。
- 按地形→区域→建筑→道路→附属物生成；约束完整轮廓、占地、树冠遮挡、入口连通、岸线和活动区。
- 生成尝试有次数上限；无合法方案则回退经过验证的备用模板，不无限重试，不因一朵花无处放置而使卡片报错。
- 仓库改名/转移后以稳定ID保持农场；布局版本固定，算法升级不悄悄重置全部地图。
- v1“位置变化”指不同仓库不同地图，以及成长时出现新元素；PNG内居民不实时移动。GIF行为动画仍属后续范围。

### 3.2 元素丰富度

下列是候选素材方向，待确认清单后制作，本轮不批量生成：

| 类别 | 候选元素 | 使用规则 |
|---|---|---|
| 建筑 | 小屋升级、鸡舍/谷仓、温室、风车 | 主屋和畜牧升级为基础，额外设施选配，不全部挤入一图 |
| 作物 | 萝卜、胡萝卜、番茄、南瓜、小麦 | 种子决定组合，阶段决定田块数量和成熟外观 |
| 林果 | 苹果/柑橘树、阔叶树、松树、浆果灌木 | 按果园、林缘成组 |
| 花草 | 向日葵、雏菊、绣球、芦苇、睡莲 | 各归属门廊、池岸或林缘 |
| 居民 | 农夫、小鸡、猫、鸭子、蝴蝶 | 基础角色加生态变体，数量封顶 |
| 庭院 | 水井、木桶、长椅、路灯、稻草人、木柴、围栏/小桥 | 依附入口、田口和岸边，有用途和归属 |

基础成长表保留阶段轮廓；物种和同职责装饰允许按种子替换。素材库丰富，单张地图仍须控制密度、保留空地。

## 4. 项目结构（确认后逐步迁移）

保留单包 Node.js + ESM + 现有 Canvas 方案，不引入 monorepo 或新前端框架。
目录按职责命名；生产服务、CLI、开发预览复用同一场景和渲染器。

```text
github-farm/
├─ src/
│  ├─ github/             # 仓库元数据、Star历史、数据归一化
│  ├─ farm/               # 稳定种子、蓝图生成、布局约束、成长规则；纯逻辑
│  ├─ render/             # 地形/物件/卡片排字、PNG导出
│  ├─ art/                # 读取manifest、素材校验
│  ├─ http/               # 图片路由、缓存、限流、错误卡
│  └─ cli.js              # 命令行生成；不重复实现业务规则
├─ config/
│  ├─ growth.json         # 阶段阈值、解锁和文案
│  └─ layouts/spring/     # 预审拓扑模板、区域候选、连通规则、扩建槽位
├─ assets/
│  ├─ source/spring/      # 原始稿、可编辑稿；运行时禁止读取
│  │  ├─ terrain/
│  │  ├─ buildings/
│  │  ├─ crops/
│  │  ├─ nature/
│  │  ├─ residents/
│  │  ├─ props/
│  │  └─ sources.json     # 来源、提示词、使用条件、哈希
│  ├─ runtime/spring/
│  │  ├─ terrain.png      # 可拼接草地、池岸、道路图块；不是固定完整底图
│  │  ├─ atlas.png        # 规范透明图集
│  │  └─ manifest.json    # 帧、脚底锚点、边界、素材版本
│  └─ fonts/              # 字体文件、LICENSE、来源说明
├─ scripts/art/           # 源稿编译、图集校验、联系表
├─ scripts/render/        # 验收样张生成
├─ test/
│  ├─ unit/               # 数据、阈值、场景规则
│  ├─ integration/        # PNG、HTTP、错误和缓存
│  └─ fixtures/           # 固定模拟数据，含缺失历史与上游异常
├─ web/                   # 仅本地预览与复制嵌入代码
├─ docs/
│  ├─ plans/              # 已评审计划
│  ├─ design/star-farm-v1/ # 概念稿、风格基准、提示词；运行时不引用
│  └─ acceptance/         # 经确认的实际渲染样张及验收记录
├─ dist/                  # 临时PNG和联系表，忽略提交
├─ .cache/                # 可丢弃数据缓存，忽略提交
├─ .env.example           # 仅变量名和假值，禁止密钥
├─ package.json
└─ package-lock.json
```

依赖方向：HTTP/CLI → GitHub数据适配 + farm → render → art。
farm 不访问网络、文件系统或真实时钟；render 不调用 GitHub 或生图。
采集数据统一成 RepoSnapshot：repositoryId、fullName、stars、newStars7d（可空）、historyWindow（可空）、fetchedAt、stale。
缓存带状态不进入成长规则；渲染接收显式数据和版本，便于复现。

## 5. 素材标准

- A 是构图和氛围基准；统一俯视角、左上光源、暖绿草地、棕红屋顶。
- 地形基础格 16px；精灵尺寸以16px倍数为优先，脚底锚点明确；全部按整数逻辑像素绘制。
- 农场层以最近邻2倍输出，不用模糊缩放；信息文字在导出分辨率绘制，保证阅读。
- 不把整张概念图机械抠开当完整素材库；按统一视角制作可复用部件，实际合成逐项核对。
- 地形共享；建筑、作物、树木、居民分层；阴影口径统一，按脚底排序。
- PNG 透明背景必须真实含 alpha；不得残留底色、切断轮廓或带固定背景色。
- 命名全部小写英文 kebab-case，例如 cottage-tier-1.png、carrot-stage-2.png；禁止 final2、新图、日期堆叠等含混命名。
- manifest 用稳定对象ID，记录矩形、pivot、footprint、visualBounds、来源ID、schemaVersion、artVersion。
- sources.json 记录每份源稿：ID、生成工具/模型（能确认的部分）、完整提示词、源文件、日期、使用条件、SHA-256；外部素材另记作者与许可证。
- 代码 MIT 与美术/字体许可分开登记；不复制星露谷游戏原始贴图。
- 运行时资产只从 source 编译产生；不手改 atlas。编译不联网、不调用模型，可在锁定环境复现。
- 新增物件先看单体、联系表和场景合成，再扩充；不要一次批量做几十种。
- 已有 assets/spring、assets/sprites、assets/scenes 暂时保留；新版禁止回退混用旧素材。确认依赖迁移后另列清理清单。

## 6. 图片服务约定

- GET /v1/farm/:owner/:repo.png：公开仓库PNG；v1不开放任意URL、尺寸和素材路径参数。
- GET /healthz：服务健康；本地预览与生产图片服务入口分离。
- 读取公开仓库计数与聚合历史；服务端Token放环境变量，用户README不含密钥。
- 每仓库缓存1小时、同仓库并发请求合并；禁止每次读图重新拉历史。
- 上游失败：最多使用24小时内旧数据并标记 STALE；无缓存返回中性错误PNG和明确错误状态，不以假农场顶替。
- 不存在/非公开仓库统一显示“Repository unavailable”；历史单独失败不阻断总数卡片。
- 应用/CDN/Camo均可能缓存；设置正确的 image/png、ETag 和缓存头，不承诺即时刷新。
- 缓存键包含仓库身份、数据版本、布局版本和素材版本；限制内存缓存数量、上游并发与单请求超时。
- 使用可运行 Canvas 原生依赖的 Node 容器；部署平台与域名在本地验收后确定，不默认上 Edge。
- 首版不必建业务数据库；缓存可丢弃，历史读取GitHub聚合接口。
- 目标单图 ≤1.5MB；先测质量与体积，不能为压缩破坏像素边缘。

## 7. 执行顺序与验收关口

| 步骤 | 交付 | 通过条件 |
|---|---|---|
| 0 设计 | 概念卡、成长对照、此计划 | 已完成；A方向确认，种子布局方向已确定 |
| 1 美术落地 | 图集、三种起步布局、成长对照 | 起步构图已确认，已生成 0、300 和 5,000 Stars 对照 |
| 2 数据与规则 | 仓库 ID、56 档、命令行渲染 | 演示模式和真实 GitHub 模式均已运行 |
| 3 图片服务 | 缓存、错误卡、一行 README 嵌入 | 两个公开仓库返回真实 PNG，缓存和错误分支通过定向测试 |
| 4 发布验证 | 公开 HTTPS、真实 README 显示 | 双语 README 与容器入口已就绪，待容器和公开地址验证 |

步骤1使用固定fixture驱动的最小渲染验证，不提前建设生产API。
先做三个种子的低阶段布局确认差异，再在各自蓝图上出中/高阶段；九张实际样图必须来自同一素材库和生成器，不能分别生图代替。
风车在步骤1登记预留位并完成5,000样张验收；不是未实现却展示的空目标。
每步完成更新本计划的状态和验收记录；不以自动化测试代替审美确认。

必要检查：阈值/掉星/缺失历史；素材清单/完整轮廓/锚点；
多种子三档和风车的通路/遮挡；同种子可复现、成长不移位、生成失败备用方案、仓库改名保持种子；长名称/Unicode；PNG尺寸；
缓存合并/限流/超时/过期；实际README的640px与窄屏显示。
更换渲染实现前先处理现有默认摆放崩溃，或在新版最小场景中证明已移除故障路径；不得声称现有build已通过。

## 8. 迁移纪律

- 现有工作区已有大量未提交修改；开发开始先记录基线，不覆盖用户改动。
- 新目录先并行建立；只复用已验证的绘制/获取工具，不沿用53周贡献布局。
- 新CLI与图片接口验收后，再切换 npm build/dev；同步修订旧 PRD、架构和双语README，说明产品从用户贡献转为仓库Star。
- 现有Python工作流尚未迁移，先保留；删除、移动或禁用前检查引用并在变更中明确说明。
- 不创建第二套长期生产生成器；新主线验收后列出旧JS/Python/素材的归档与清理范围，执行前供用户复核。
- 本轮不创建上述待建目录、不安装依赖、不修改工作流、不提交Git或部署。
